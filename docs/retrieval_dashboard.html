2分档表现（Hit@5）

查询按难度分四档，越往后越难。最关键的对比在 T4 语义改写档。

T4（语义改写）是特意造的：先用脚本确认「纳凉」「老建筑」「古董」「字画」在语料里出现 0 次， 再拿这些词提问。结果 —— 关键词检索 Hit@5 = 0%，混合检索 80%。 这是"必须上语义检索"最硬的证据。

3评测反查出的真实 bug

评测不只是打分，它暴露了检索链路里两个靠"看代码"发现不了的问题。

修复前 · 纯关键词检索
「西安兵马俑值得去吗」
  1. 兵马俑 + 华清宫一日游（跟团游记）
  2. 兵马俑 + 华清宫一日游（跟团游记）
  3. ……前 10 条全是"跟团游记"
Top-10 命中率：0%
修复后 · 混合检索 + 景点名精确匹配
「西安兵马俑值得去吗」
  1. 秦始皇帝陵博物院(兵马俑)
  2. 秦始皇帝陵博物院(兵马俑)
  3. 秦始皇帝陵博物院(兵马俑)
Top-1 命中，T1 档 Hit@1：83.3% → 100%

根因：那些"跟团游记"标题里写了"兵马俑"，而 兵马俑自己的评论反而不含这三个字（游客写的是"太壮观了""人好多"）。 解决办法是用最长公共子串 ≥ 3 字判断"用户点名了哪个景点"，命中后把该景点的评论直接提进候选池。 第二个 bug 是同一景点多条评论挤满 top-k，靠按景点多样性重排解决。

4混合检索是怎么组成的

三路信号并行召回，用 RRF 融合排名，再按景点去重重排。

BM25 关键词字符 n-gram 召回，抓精确词面
向量语义MiniLM 句向量，抓换说法
景点名精确匹配最长公共子串 ≥ 3 字，抓"点名"
→
RRF 融合得分 = Σ 1/(60 + rank)
只用排名，不用分数 —— 省掉余弦相似度与 BM25 分的量纲对齐
→
景点去重重排同景点最多 1 条；
被点名的景点不受限
→
Top-K 输出连同出处一起喂给大模型

为什么用 RRF 而不是加权求和：加权求和要先把两类分数归一化，多一层出错空间； RRF 只用"排第几"，天然免疫量纲差异。
